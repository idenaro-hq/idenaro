Article 21(2)(e) requires security to be embedded in the acquisition, development, and maintenance of network and information systems, including vulnerability handling and disclosure. This covers the full software development lifecycle and system configuration management.

A finding mapped to this article means the scanner detected a security control that should have been implemented during development or system configuration and has not been maintained correctly in production.

### What it means in practice

This is the broadest category of web application security findings: missing or misconfigured HTTP security headers (HSTS, X-Frame-Options, X-Content-Type-Options), absent Content Security Policy, CORS policies allowing unintended origins, insecure cookie attributes, open redirect vulnerabilities in authentication flows, user enumeration weaknesses, and exposed debug or management endpoints that should have been disabled before production deployment.

### Compliance obligation

- Security headers must be part of the standard deployment baseline - not optional post-launch additions.
- CORS and CSP policies must be reviewed and hardened as part of each release cycle.
- Authentication flows must be tested for open redirect and enumeration vulnerabilities before deployment.
- Debug endpoints, actuator interfaces, and development tooling must be disabled or removed in production builds.
- Cookie security attributes (Secure, HttpOnly, SameSite) must be enforced at the framework level.

### Enforcement context

Art. 21(2)(e) places the compliance obligation at the development process level - meaning regulators can find non-compliance even if a vulnerability has not been exploited. Systematic absence of baseline controls signals a process failure, not just a configuration oversight.
